> Most ML developers pick a lane and stay there. I went sideways — cardiovascular risk, nanomaterial stability, crypto forecasting, autonomous agents. Not for breadth. To answer one question repeatedly: *what does this domain actually need from a model that most practitioners miss?*
>
> In cardiology it's **calibration**. In nanoscience it's **physics-informed features**. In agentic AI it's **judgment**. Every project in this profile is a deployed product with a live URL and every design decision I can defend under questioning.

<!-- ═══════════════════════════════════════ PHILOSOPHY ═══════════════════════════════════════ -->

<sub>ENGINEERING PHILOSOPHY</sub>

<br/>

<table>
<tr><td width="28"><sub><b>01</b></sub></td><td><b>Calibration over accuracy</b> in high-stakes domains. A model that says 73% should mean 73%. Accuracy tells you how often it's right. Calibration tells you how much to trust it when uncertain.</td></tr>
<tr><td><sub><b>02</b></sub></td><td><b>Domain knowledge belongs in the model design</b>, not just the writeup. Physics-informed features for nanoscience. Median imputation over SMOTE for medical data. The domain constrains the solution.</td></tr>
<tr><td><sub><b>03</b></sub></td><td><b>A model that doesn't ship doesn't exist.</b> Every project here has a live URL. Not because deployment is glamorous — it's tedious — but because the only way to know if something works is to run it in the real world.</td></tr>
</table>
